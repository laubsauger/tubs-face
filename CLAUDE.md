# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev           # Start dev: tsx watch server + vite client (concurrent)
npm start             # Start production server (compiled dist/)
npm run build         # Build client (vite) + server (tsc)
npm run typecheck     # Full TypeScript validation (both configs)
npm run test          # vitest run
npm run bench:llm     # Benchmark LLM performance

# Python deps (if not using the committed venv/)
pip install -r requirements.txt
npm run setup-ming    # venv-ming for the cloned voices (Apple Silicon); the server starts Ming once it exists
```

## Branches

`main` is the only long-lived branch. Work that takes more than one sitting goes on a short branch from `main`; merge it back (a PR) once it works and delete the branch.

## Run on a studio Mac (a studio-manager service)

First-time setup, step by step (Gemini key, voices, start, checks): `docs/SETUP-STUDIO-MAC.md`. `npm ci` sets up the speech service, the Ming voices (Apple Silicon) and a `.env` from `.env.example`; the voice references are in git (`assets/ming-voices/`). The default voices are Ming (`ming:friend`, `ming:friend-b`); Kokoro is only a deliberate choice in `.env`, and a missing Ming is an error, never a quiet switch.

Install once: Node 24, `npm ci`, the speech service's Python venv (`venv/`, `pip install -r requirements.txt`), `npm run setup-ming` (`venv-ming/`, Apple Silicon), Google Chrome (the face pages run in it). The site node (mediamtx) comes from studio-manager; its user `tubs` may only publish, on `~^tubs-`.

Copy the private files, never in git: `.env` (`GEMINI_API_KEY`, `LLM_PROVIDER`, …), `data/face-library.json` (the people Tubs recognises) and the site login, `data/site-login.json`: `{"user": "tubs", "pass": "…"}` (`chmod 600`; also `user:pass` or two lines). `data/tubs-state.json` is created on the machine.

```bash
PORT=3100 TUBS_STUDIO=1 TUBS_STUDIO_SITE=http://127.0.0.1:8889 \
TUBS_STUDIO_SITE_AUTH=data/site-login.json TUBS_STATE_FILE=data/tubs-state.json TUBS_TONIGHT_FILE=data/tonight.json \
TUBS_MIC_SOURCE=off TUBS_VISION_SOURCE=off \
REALTIME_KOKORO_VOICE=ming:friend SECONDARY_VOICE=ming:friend-b DUAL_HEAD_ENABLED=true DUAL_HEAD_MODE=llm_directed \
npx tsx src/server/index.ts
```

- Health check: `GET /healthz` is 200 once the speech service, Ming (for `ming:` voices) and, in studio mode, both face pages are up, else 503; `GET /health` shows each part.
- The site login reaches only the face pages (an Authorization header for WHIP; `TUBS_STUDIO_SITE_READ_AUTH` for WHEP reads if the site needs one); never in env values, URLs, `GET /studio` or the log. A missing file or a refused login (401) shows as each head's error in `GET /studio`; a refused login is retried every 30 s.
- The Studio tab offers the mic and vision sources as pick lists (`GET /studio/sources`): this Mac's devices (from the listener page), the site node's live paths (its mediamtx API, `TUBS_STUDIO_SITE_API`, default the site host on :9997; login `TUBS_STUDIO_SITE_API_AUTH`, else the read login) and, with `FLEET_HUB` set, the floor plan's placed depth cameras as snapshots.
- Face recognition on the server instead of in the listener page: `FACE_SERVICE=local` (or `http://<box>:3004`, `fleet:faces`), `docs/face-service.md`. The service (`src/face-service.py`, the speech service's `venv`, `requirements-faces.txt`, ffmpeg) reads a `site:` stream over RTSP or a `snapshot:` URL; its models download once into `~/.cache/tubs-face/models`. A local camera stays with the listener page. `GET /studio` `parts` shows it as `recognition`.
- `TUBS_STATE_FILE` keeps the operator's choices across restarts: the preset, the vision provider and model, the mic and vision sources, the switches (camera, face recognition, vision descriptions, relationships, mic), what each head wears (never a key).
- `TUBS_TONIGHT_FILE` keeps tonight's memory across restarts (`memory/tonight-file.ts`): the field notes, quotes, who was seen and when, turns, and the unnamed visitors' auto-onboarding snapshots. It is visitor data and stays on this machine's disk only (`data/tonight.json`, gitignored, mode 600); written atomically a few seconds after a change and on SIGTERM, at once when the operator forgets someone or clears tonight in the memory view; anything older than `NOTES_TTL_MS` (12 h) is dropped on save and on load. Unset, the memory is memory only.
- The face windows open off screen (`TUBS_STUDIO_WINDOWS=offscreen`, the default): small, in the far corner (macOS keeps a corner of every window on a screen), never minimised (a minimised page stops drawing, so its stream would freeze); the launcher moves them over `--remote-debugging-pipe` (no port) and gives the focus back to the app that had it. "Show face windows" in the Studio tab (`POST /studio {windows: 'visible'}`) brings them on screen. A page whose Chrome exits is reopened, each time logged with its reason, until 3 exits within a minute; then it stays closed with an error in `GET /studio`.
- `TUBS_STUDIO_DEBUG_PORT=9230` (off by default): main's face page on that DevTools port, small's on the next, 127.0.0.1 only; read the listener page's console with chrome://inspect or `http://127.0.0.1:9230/json`.
- Stop with SIGTERM. The Python speech service, Ming and the face pages' Chrome run in their own process groups under a guard (`processing/owned-process.ts`), so even a SIGKILLed server leaves nothing behind.

## Architecture

Three-layer TypeScript system: **React frontend** → **Node.js server** → **Python STT/TTS microservice**.

Monorepo with shared type-safe contracts. Build: Vite (client) + tsc (server). Dev uses `tsx watch` for server hot-reload.

### Server (`src/server/`) — TypeScript, port 3000

**Entry:** `index.ts` — HTTP server + WebSocket init

- `ws/server.ts` — WebSocket server, client tracking, message routing, broadcast
- `assistant/service.ts` — LLM orchestration, turn management
- `assistant/dual-head.ts` — Structured multi-beat responses (actor/action schema)
- `assistant/context.ts` — Conversation history
- `assistant/fillers.ts` — A short pre-rendered sound ("Hmm.") at the start of some voice turns, in main's voice, while the reply is generated; rendered at startup once Ming is ready
- `assistant/emotion.ts` — Emotion extraction
- `assistant/text.ts` — Output normalization, TTS sanitization
- `assistant/sentence-splitter.ts` — Break responses into utterances
- `assistant/prompt.ts` — System instruction builders
- `assistant/vision.ts` — What Tubs sees: camera pictures described for the reply prompt (`docs/vision.md`). Provider `off` (no picture leaves the server), `gemini`, or `openai` (any OpenAI-compatible `/chat/completions`, or `fleet:vision`, a box picked by the studio-manager hub at `FLEET_HUB`), all live via `POST /config`; the Studio tab picks the server and model without jargon (`routes/vision-routes.ts`, `vision/servers.ts`, local network only: `GET /vision/servers` lists Ollama here, `fleet:vision` and each fleet vision box by name, `GET /vision/models?base=` what a server has from `/v1/models` or Ollama's `/api/tags`, thinking variants flagged with the `-instruct` one suggested, `POST /vision/test` one picture to a provider/model/server, same-origin JSON, outside the cap and stats); hourly cap, no refreshes while asleep, last description kept on failure; counts in `/stats` `vision`. Parts in `vision/` (`budget.ts`, `fleet.ts`, `providers.ts`, `stats.ts`). Env: `VISION_PROVIDER`, `VISION_MODEL`, `VISION_BASE_URL`, `VISION_API_KEY`, `VISION_MAX_PX`, `VISION_TIMEOUT_MS`, `VISION_REFRESH_MS`, `VISION_MAX_PER_HOUR`, `VISION_WHILE_ASLEEP`
- `assistant/relationships.ts` — How Tubs treats people he recognises (`config/relationships.json`, in git; folder `TUBS_CONFIG_DIR`; `GET/POST /relationships`; toggle `relationshipsEnabled`, on by default). The line rides with the current turn only (`context.ts`), never in history or field notes, and goes once the face page's `people` no longer name the person for `RELATIONSHIP_GRACE_MS` (10 s) or that page disconnects
- `assistant/bits.ts`, `routes/bits-routes.ts` — Running bits: the characters' running gags and traits (the projector remotes, Dimi and the rent, Alan Watts, the studio Wi-Fi, the body, Small hiding things) as data in the preset, `bits: [{id, text, match, cooldownMin, chance?, head?}]` (`shared/contracts/bits.ts`; a preset without `bits` gets `tubs.json`'s). They are not in the static persona: `variety.ts` offers one in the stage direction on about 15 % of turns ("If it fits, … may use this"), enabled and off cooldown only; a spoken line of either head that matches it (plurals count) starts its wall-clock cooldown; used in the last 10 minutes, or again during its cooldown, it goes into the "stay off" line, next to the worn words `variety.ts` counts over both heads and per head (last ten replies or last half hour, plurals as one). One generation call per turn: nothing reruns, filters or rewrites a reply; what a reply used only shapes the next direction. `GET /bits` (uses tonight, last used, cooldown left, on/off, the stay-off list), `POST /bits {id, enabled}` (for tonight, not saved); the dashboard's Mind tab shows them
- `memory/view.ts`, `routes/memory-routes.ts` — The memory view's data: one card per person (tonight's field notes, the face library's samples and photos, the relationship, in view or not), `GET /memory`; photos at `/memory/photo/<face id>` (the library keeps an 80 px JPEG per sample) and `/memory/snapshot/<visitor id>` (an unnamed visitor's first auto-onboarding snapshot, memory only like the notes). Admin actions are same-origin JSON POSTs (`/memory/forget {key}`, `/memory/library/remove {name}`, `/memory/clear`); all of it answers the local network only. A library removal broadcasts `faces_changed` so the face pages stop recognising that person. `TUBS_FACE_LIBRARY` moves the library file (tests). The face library is curated in the cards, photo by photo: each sample carries the audit's flag (`faces/audit.ts`: it reaches the 0.65 match threshold against someone else's sample, "looks like Flo · 75%", or none of its owner's other samples reaches 0.35, "unlike Rapha's others"; `GET /memory/library/audit`, similarities only), and can be removed or moved to the person it resembles (`/memory/library/samples/remove {ids}`, `/memory/library/samples/move {ids, to}`: the sample keeps its embedding, photo and time), alone or selected together; every confirmation says what happens with names and counts (`ui/panels/memory-text.ts`); the last change can be undone for a minute (`/memory/library/undo {undo}`). Every library write goes through `faces/library.ts` `writeFaceLibrary`: the file as it was is copied first into `face-library.backups/` next to it (mode 600; kept: the newest 20, and for 7 days the first of each burst of edits and the newest of each day), the new one is written whole (temp file, rename), and the change is logged with its origin (route and address, the face service's onboarding, auto onboarding) to `face-library.log` and the server log, no embeddings. "Restore from backup" in the memory view lists the backups (`GET /memory/library/backups`: who with how many, and what a restore brings back) and restores one exactly (`/memory/library/restore {backup}`; the library it replaces is backed up too)
- `presets/presets.ts`, `routes/preset-routes.ts` — Character presets: who the characters are (persona template inline, from a `.md` next to the preset, or the built-in one; the extra instruction; canned lines; running bits), a voice per head, the look (every `glitch*` setting, Small's colour and each head's prop) and behaviour (sleep timing, interruptible, two-head mode), in `config/presets/<name>.json` (`TUBS_CONFIG_DIR`, in git; `tubs.json` is the built-in character). `GET /presets`, `POST /presets {name}` saves the current state, `POST /presets/apply {name}` applies one live, all or nothing (config broadcast; no restart, the faces keep publishing). `GET /studio` lists them under `presets` (names, active)
- `assistant/field-notes.ts` — Tubs's notes on tonight's visitors, per face-tracker person id: one head writes hidden `[[NOTE: …]]` / `[[QUOTE: …]]` / `[[NAME: …]]` tags (never spoken), two heads a `notes` field in the reply JSON (`dual-head.ts` schema; hidden tags in a spoken line were almost never written). A note goes to the person in view, or to whoever was in view up to `IN_VIEW_GRACE_MS` (15 s) ago (the face page's list empties whenever a face is missed for a frame); a recognised person under a new id (face pages reloaded, server restarted) gets what was noted under the old one. Shown in the Mind and People tabs (who is in view) and the memory view (everyone tonight); kept across restarts, with the unnamed visitors' snapshots, with `TUBS_TONIGHT_FILE`
- `llm/provider.ts` — Router: Gemini, or Ollama/OpenAI via the Python service (`LLM_PROVIDER` env); both stream
- `llm/gemini-client.ts` — Gemini API streaming with SSE
- `llm/providers/gemini.ts` — Structured generation wrapper
- `llm/providers/realtime.ts` — Gemini Realtime/Live API
- `processing/speech-service.ts` — Starts and supervises the Python speech service and the Ming TTS service
- `tts/stream.ts` — Streaming audio chunks to WebSocket
- `config/runtime.ts` — Runtime configuration, session stats
- `routes/api.ts` — REST: `/health`, `/stats`, `/config`, `/speak`, `/faces`, `/api/*`
- `faces/` — The face library (`library.ts`) and, with `FACE_SERVICE` set, studio face recognition on the server (`docs/face-service.md`): `service.ts` talks to the face service (supervised like Ming for `local`, NDJSON stream of frames), `recognition.ts` does with its frames what the listener page does with its worker's (library match with `client/face/matching.ts`, the people and visitor trackers, auto onboarding, vision pictures, dashboard onboarding), `studio-faces.ts` wires it to the studio settings; one `FaceObservation` per frame (`contracts/studio.ts`) to the listener page, the dashboards and `GET /studio/faces`
- `recordings.ts` — Face-window video recordings, appended piece by piece; on stop ffmpeg re-encodes the video (Chrome's file freezes in QuickTime after the tab is resized) into a plain MP4 in `~/Movies/tubs-recordings` (`TUBS_RECORDINGS_DIR`), and Chrome's own file is kept in its `raw/`. `scripts/check-playback.swift` tells whether a video plays to the end in the Mac's decoder
- `studio/` — Studio mode (sentient-studio `docs/contract.md` §5-6), off by default (`TUBS_STUDIO`). `GET/POST /studio {enabled, site, micSource, visionSource}` (`routes/studio-routes.ts`; `GET /studio/snapshot` proxies a `snapshot:` source for the page); `GET /studio/sources` (`sources.ts`, contract §6 additive, for the Studio tab and the sentient panel): `{micSource, visionSource, mic: [...], vision: [...], suggested: {mic?, vision?}, problems: [...]}`, each entry `{value, label, kind: off|local|site|snapshot, ready, tracks?}`: `off`, `local` and the listener page's devices as `local:<label>` (its `studio_status.devices`; ready while it is connected; labels unlocked by opening each kind once for a moment, `client/studio/devices.ts`), the site node's paths with audio (mic) or video (vision), never `tubs-*` or `os-*` (mediamtx `/v3/paths/list`, ready = publishing), and with `FLEET_HUB` set the floor plan's placed depth cameras, `snapshot:<their service base>/api/snapshot/color.jpg` (ready = service healthy; a hub that does not answer adds nothing and no problem); `suggested` names the only ready remote source when the current one is not ready; the Studio tab asks on open and every 5 s; the dashboard has no mic or camera in studio mode, so the listener page reports what it hears and sees (`live.ts`, `pulse.ts`, `client/studio/live.ts`, `client/studio/watch.ts`): a dashboard says what it shows (`studio_watch {live, video}`: live while it is on screen, video while the People or Studio tab or the onboarding dialog is open) and the listener sends only that (`studio_live` ~10 Hz: the same app state fields a face window shares with a dashboard, so the Voice and People panels and the status bar show the studio mic and the face worker's detections with their top candidates; `studio_frame`: a 320 px JPEG a few times a second, drawn with the face boxes by `face/overlay.ts`); a site-stream camera is read live by the dashboard over WHEP (`client/studio/camera-stream.ts`, relayed pictures as fallback); onboarding from the dashboard runs on the listener's camera (`studio_face_call {id, method, args}` answered by `studio_face_result {id, ok, value|error}`, methods `STUDIO_FACE_METHODS` in `contracts/studio.ts`: `beginEnrollment`, `endEnrollment`, `captureEnrollmentSample {previous, choose?}` (`choose`: the box `[x, y, w, h]` 0..1 of the face to take when several are in view, matched by overlap; without it exactly one face must be in view), `saveEnrollment {name, samples}`, and `embedPicture {image}` (added for uploads: a `data:image/jpeg|png|webp` URL up to 12 MB, run through the same detect, align and embed path on the listener's face worker; the face service answers the same calls while it recognises (`faces/recognition.ts`, the choose box matched the same way, `chosenFace` in `client/face/matching.ts`; embedPicture through its `POST /detect`, which returns each face's thumbnail too); a still camera takes a fresh picture per pose); face library edits broadcast `faces_changed` (debounced) so every page reloads its copy; `GET /studio/pulse` (local network, polled ~4 Hz, each poll keeps the listener reporting 3 s; also pushed as `studio_pulse` to watching dashboards): `{t, mic: {source, level, state: off|listening|hearing|thinking|speaking}, speaking: main|small|null, heard: {text, t}|null, seen: [{name, prob, box: [x, y, w, h] 0..1}], vision: {provider, lastMs, at}}`; `GET /studio` `parts` (`parts.ts`, the Studio tab's top card, read by the sentient panel too): `[{id: brain|voices|realtime|vision|mic|faces|site, label, where, ok, detail?}]`, `where` the host or host:port doing the work (this machine's name for loopback, fleet:vision resolved to its box, the mic's device or site path, the face pages' Chrome), `ok` null when not in use or not known yet, from cached health probes and the last LLM and vision calls (never a network wait); recognition names the faces (matching, relationships) and auto-onboards; with both off the face worker never loads; parts `camera`, `recognition` (the face worker: where, ok while it checks pictures, "SCRFD+ArcFace · threads · ms · fps · people") and `relationships`; boxes with detection score, candidates against the threshold, the decision); the operator face window watches the studio listener too (it lets go of its own mic and camera in studio mode, and of deciding when Tubs sleeps); `/?view=dashboard&tab=people` opens the dashboard on that tab; `GET /studio/vision` (local network): the last vision check (provider, model, where, ms, text or error), camera and vision on or off, the relationships in effect; keyframes come only when the site node asks (mediamtx: every 2 s), since forcing them by restarting the encoder held a frame each time; the WHIP answer gets `x-google-start-bitrate` so a new publish doesn't drop frames while the bitrate ramps; `launcher.ts` opens one system Chrome per head (own profile in the temp dir, closed on disable, on shutdown, and left over from a killed server via the profile's SingletonLock) unless `TUBS_STUDIO_LAUNCH=external`. ### Face service (`src/face-service.py`, `src/face_pipeline.py`)
- SCRFD det_10g + ArcFace w600k_r50 on onnxruntime (CoreML as an FP32 ML program on a Mac, CUDA if present, else CPU), copying the browser worker's preprocessing exactly so the library's embeddings stay valid (cosine 0.99998 to the browser, `tests/face-compat/run.ts`, `tests/python/test_face_pipeline.py`); stdlib HTTP on `FACE_SERVICE_PORT` (3004): `/health`, `/source`, `/observations`, `/frame.jpg`, `/thumbnail`, `/capture`, `/detect`

### Python Service (`src/realtime-processing-service.py`)
- Flask app on port 3002, started and restarted by the server
- STT: `lightning-whisper-mlx` (Apple Silicon) or `faster-whisper` (CPU, int8). Clips in which Silero VAD (bundled with faster-whisper) finds under `REALTIME_VAD_MIN_SPEECH_MS` (250) of speech skip Whisper; transcripts Whisper scores as no speech are dropped too
- TTS: Kokoro (MLX on macOS, native elsewhere), streamed per sentence over `/tts/stream`; or system TTS (macOS `say`, pyttsx3 elsewhere)
- LLM proxy for Ollama / OpenAI-compatible models: `/llm/generate`, `/llm/stream`
- Endpoints: `/transcribe`, `/tts`, `/tts/stream`, `/llm/*`, `/health`
- Voices starting with `ming:` (`ming:friend` is main Tubs' cloned voice, `ming:friend-b` Mini's) are forwarded to a separate Ming TTS service at `MING_TTS_URL` (default `127.0.0.1:3003`), with the part after `ming:` as the voice name. When Ming is down or still loading, a `ming:` voice fails with Ming's reason (server log, and the turn's error in the transcript); it never switches to a Kokoro voice. With both heads on Ming, Kokoro isn't loaded. Start Tubs with `REALTIME_KOKORO_VOICE=ming:friend SECONDARY_VOICE=ming:friend-b DUAL_HEAD_ENABLED=true DUAL_HEAD_MODE=llm_directed`; runtime config does not survive a restart. Ming is `src/ming-tts-service.py`. It needs a newer mlx than STT, so it runs from its own venv, `venv-ming` (`npm run setup-ming`, pinned in `requirements-ming.txt`). The server starts and supervises it when that venv exists, unless something already listens on `MING_PORT` (3003). Its voice references are in git, in `assets/ming-voices/` (a local `data/ming-voices/` or `MING_VOICE_DIR` overrides them); the listening tests behind its settings are in `~/Movies/tubs-voice-lab/`. Its output gets a warmer EQ per voice (`src/ming_eq.py`, the user's pick from the voice lab), filtered chunk by chunk with the state carried over. Ming gets whole replies, not sentences, and streams each back in chunks from its `/tts/stream` as it renders (falls back to its `/tts` if that route is missing). The chunks of one reply carry the same text, all but the last flagged `more`; the client plays them back to back under one subtitle, in a 24 kHz AudioContext so the mid-word cuts join sample for sample.

### Client (`src/client/`) — React + TypeScript + Zustand

**Entry:** `main.ts` → `bootstrap-react.tsx` (initializes runtimes, React root)

Two build entries: `index.html` (main) and `app-mini.html` (mini display mode). Pages are cross-origin isolated (COOP/COEP `credentialless`, in `vite.config.ts` and `src/server/http/static.ts`) so the face worker (`src/workers/face-worker.ts`, SCRFD det_10g + ArcFace R50 on onnxruntime-web) runs on up to 8 WASM threads; the benchmark behind it is in `~/Movies/tubs-face-lab/`. `/?view=dashboard` is the operator HUD for a separate screen (no face, no audio, mic or camera); `app-mini.html?embed=1` is the mini tile inside the face window. The dashboard's Studio tab (`ui/panels/StudioPanel.tsx`) runs the studio: studio mode, mic and vision sources, the vision provider, each head's stream, presets and the relationships list; it works inside the sentient panel's cross-origin iframe. `/?view=memory` is the memory view on its own (`memory-page.tsx`, HTTP only); the dashboard has it as the Memory tab (`ui/panels/MemoryPanel.tsx`). `studio-face.html?actor=main|small[&size=1024][&monitor=1]` is one head for the studio (`studio/runtime.ts`): face alone on black, drawn at most 60 fps (`STUDIO_RENDER_MAX_FPS`; it is published at 30), canvas plus that head's voice published over WHIP to `<site>/tubs-<actor>/whip` (`studio/publisher.ts`, `transport/whip.ts`), gaze and presence from the director. The main one is also the listener (mic, sleep, proactive); while studio mode is on the operator face lets go of its mic.

**Runtime-based architecture** — each subsystem is a standalone runtime with `init()`, `bind()`, `dispose()`:

- `audio/speech-runtime.ts` — Server audio playback (streaming queue), subtitle timing. `audio/streaming-session.ts` plays one turn's chunks back to back; a reply still arriving (Ming's `more`) starts only once enough of it is here to play through at the measured delivery rate (Ming renders at ~0.4x under GPU load; `STREAM_MAX_HOLD_MS`), and a line never ends while more of it was promised, so a stalled reply stays one subtitle and one studio caption
- `audio/screen-recorder.ts` — Record button / R key: this tab's video and audio plus the mic, mixed, uploaded to the server each second
- `audio/voice-runtime.ts` — Mic input + VAD (push-to-talk + hands-free). With the Interruptible toggle (config `interruptible`, Voice panel; off by default), talking over Tubs or Mini cuts them off hands-free; off, the mic ignores speech while a head talks
- `audio/ambient-runtime.ts` — Background sounds
- `face/runtime.ts` — Face shell, camera input, face detection. The People tab's library dialog shows one block per person and a thumbnail row per capture session (`face/library-sessions.ts`: samples under 5 minutes apart; the library keeps times, not sessions), with rename and remove per person, remove per session and per sample, and Add photos per person (capture from the camera, or upload pictures, each refused with its reason unless it holds exactly one face). Onboarding adds to someone the library knows: with a recognised face in view the People tab's button is "Add photos to <name>" ("Someone else…" opens the usual flow); the wizard's name field suggests the library's people (thumbnail, sample count) and a typed name that is one of them (case and spaces aside) adds to them; with several faces in view the wizard asks which box. Before samples go into an existing person their similarity to that person's samples is shown (`face/person-match.ts`: the mean of each new sample's best cosine), and under `FAR_OFF_SIMILARITY` (0.5), or when another person matches them clearly better (by 0.05: a wrong pick, or a person whose samples are already mixed up with someone else's), the operator confirms first ("These look like a different person: 31%", "These look more like Flo (77%) than Dimi (54%)"). The server keeps one name per person: `POST /faces` and a `PATCH /faces {id, name}` rename take the existing spelling of a name that differs only in case or spaces (`faces/library.ts` `canonicalPersonName`)
- `face/matching.ts`, `face/settle.ts` — Who a face is: a frame names the library's best match only at 0.65 or more and 0.12 ahead of the next person; a track (the face service's, or followed by overlap) is named once 2 of its last 3 fresh embeddings agree (or one very clear one), and keeps the name until another person gets as many; the listener page and the server both use it, and greetings, relationships and notes see settled names only (`docs/face-service.md`); an arrival's greeting waits up to `GREETING_NAME_WAIT_MS` (2.5 s, judged on each check) while a name is on its way (`createGreetingHold`), on the listener page as in the service. `src/scripts/face-library-audit.ts` (spread, closest people, samples that name each other; no embeddings printed) and `src/scripts/face-name-replay.ts` (old vs new naming on recorded checks)
- `face/behavior-runtime.ts` — Expression & animation synced with speech. The studio director's look is followed smoothly while it moves (`face/gaze.ts` pursuit) and held with fixations, micro-saccades and glances once it is steady
- `glitch/runtime.ts` — Pixel face with glitch effects (WebGPU only). A studio head is laid out in its stream's square (`studioCanvasPx`), never in its window, so the window's size cannot change the face. Sub-pixel motion on the pixel grid is drawn as quad edges stepping a pixel, different ones each frame, which read as the faces jittering on the studio projectors; so between deliberate motions (glances, saccades, blinks, expressions, talking) the shapes hold still: breathing is a brightness swell (`MOTION.breathLight`, `face/sleep-life.ts` asleep), there is no slow drift or swell, and the scanlines have soft edges (the share of each screen pixel they cover) and roll slowly (`glitchScanlineSpeed` 3 px/s, was 26). Asleep the shapes hold still between twitches (a lid flicker, mouth shift or glance every 6 to 15 s) and the scanlines stop
- Build: onnxruntime-web is its own chunk in the worker build (`vite.config.ts` `worker.rollupOptions.output.manualChunks`): its WASM threads start as workers of its own module, and bundled into the face worker each thread loaded the face worker instead, so a built page never got a ready face worker (dev was unaffected); `src/workers/face-worker-build.test.ts` builds and checks it
- `glitch/props.ts` — What each head wears (config `propMain` / `propSmall`, ids `PROPS` in `contracts/config.ts`, set live by `POST /config`, a 400 names the valid ones): a hat drawn on the face's own pixel grid and through its shader, so it follows the eyes' tops (expressions, motion, a tilt), glitches and takes the mood like the face, and is in every studio stream. A studio frame moves the face down so the hat stays inside it at full upward gaze (`STUDIO_PROP_TOP`); a screen fits face and hat together. Picked in Settings > Props
- `fx/runtime.ts` — Visual effects (filters, overlays)
- `behavior/emotion-runtime.ts` — Emotional state: the face window's mood, and each studio head's own (impulses from that head's lines; two-head `audio_chunk`s carry their line's emotion)
- `behavior/proactive-runtime.ts` — Proactive/greeting responses
- `transport/ws-client.ts` — Managed WebSocket with reconnection
- `state/app-state.ts` — Zustand store with `subscribeWithSelector`
- `handlers/messages.ts` — Routes WS messages to state updates
- `ui/app-shell.tsx` — Shells (face, dashboard, mini, spectator) and the operator hotkey router
- `ui/hud/` — Operator HUD: status bar, tabbed dock, floating transcript, mini tile; pure rules in `dock-state.ts`, `hotkeys.ts`, `transcript.ts`
- `ui/window-link.ts` — BroadcastChannel between face, mini and dashboard windows (presence, device-state relay)

## WebSocket Protocol

Messages are JSON with a `type` field. Full types in `src/shared/contracts/ws.ts`.

**Client → Server:** `ping`, `incoming`, `interrupt`, `face_motion`, `face_blink`, `head_speech_state`, `presence`, `camera_frame`, `appearance_frame`, `tts_request`; studio mode: `studio_look`, `studio_presence`, `studio_context`, `studio_stage` (director, ignored while studio mode is off), `studio_state`, `studio_status`, `studio_caption` (face pages, `/ws?studio=<actor>`)

**Server → Client:** `ping`, `config`, `system`, `expression`, `faces_changed`, `thinking`, `speak`, `speak_chunk`, `speak_end`, `audio_chunk`, `turn_start`, `turn_script`, `turn_context`, `interrupt`, `backchannel`, `incoming`, `donation_signal`, `stats`, `stream_debug`, `conversation_mode`, `sleep`, `wake`, `error`, `face_motion`, `face_blink`, `head_speech_state`; studio mode: `studio_config` (face pages, and other pages while studio mode is on), `studio_look`, `studio_presence`, `studio_stage` (face pages only), `studio_state`, `studio_caption` (everyone; the line a head says and how many of its characters have been heard, from its page's playback clock, `studio/caption.ts`)

## Key Patterns

- **Runtime composition** — features are standalone runtimes, not class hierarchies
- **Streaming-first** — audio chunks streamed incrementally (not full responses)
- **Dual-head** — structured multi-beat responses with different actors/actions
- **Broadcast model** — server broadcasts all messages to all connected WS clients
- Requires `GEMINI_API_KEY` env var
